## 1. 做了什麼

### 階段一：`@tangent/client`（[`import-assembly-merge.ts`](../../web/packages/client/src/import-assembly-merge.ts)，由 `index.ts` 匯出）

- `SessionMerge { targetKey, absorbedKeys }`；`addSessionMerge`（至少 2 個不同的可見段落；有 `preferredTargetKey` 時以它為目標，否則取時間序最前者；已合併過的段落會把自己的 `absorbedKeys` 一起帶進來攤平成同一筆，順序依目前的時間序）、`removeSessionMerge`、`applySessionMerges`。
- `applySessionMerges(sessions, merges, edits)`：
  - 第 k 個被併入段落（k ≥ 1）的訊息 `externalId` 改為 `m${k}_…`，重問／重新生成支線的 `anchorExternalId` 同步改；目標段落保留原 id。
  - `edits.messages[被併入]` 的角色切換與移除以新 id 併入 `edits.messages[目標]`；`edits.attach` 中掛在被併入段落的支線轉址到目標的新 id；被併入段落自己的 `roles`／`attach`／`conclusions` 在合併後的視圖中拿掉（原始 edits 不動）。轉址後會掛在自己身上的點也拿掉（改用預設掛點）。
  - 合併後：標題、key、來源、檔名沿用目標；`createdAt` 取各段最早的真實開始時間，`updatedAt` 取最晚；每段若有手動時間，先把位移寫進該段訊息的時間，合併後的段落 `manualTime` 等於開始時間（位移為 0，不會重複位移）。
  - `mergedCounts.get(target) = 1 + 被併入篇數`；輸出依輸入順序，被併入的段落濾除。
- `mergedOrigin(sessions, merges, key, externalId)`：把合併後的 id 對回原段落與原 id（檢查該段真的有這則）；`mergeMembers(merges, key)`：一篇代表哪些原始段落。
- `applyBatchRole(edits, sessions, keys, role, targetChapterKey?)`：批次設角色；支線角色加上指定章節時，以 `defaultAttachMessage(章節, 該篇開始時間, edits)` 寫入掛點，章節自己不會被設成支線。
- `moveSessionsToIndex(order, keys, targetIndex)`：單篇時與 `placeSession` 相同；多篇保持彼此順序整組移動。
- 沒有頂層的非純運算（全是函式宣告與 `const` 箭頭函式）。

### 階段三：右欄與拖放

- [`drop-zones.tsx`](../../web/apps/demo/src/frame/f14/drop-zones.tsx)：
  - 右欄頂端置頂的三個分類區 `data-tg-drop-zones`（`data-tg-drop-role="chapter|merged_branch|standalone"`）。拖曳時虛線框加底色，滑過時加外框。**也是按鈕**：按下會把角色套用到已勾選的段落（不拖曳的路徑），沒有勾選時 `aria-disabled`。

  - 獨立對話清單 `data-tg-drop-standalone-list`：拖曳中即使還沒有獨立對話也會出現放置框。

## 2. 和工單不同的地方

1. **沒有從 `import-assembly.ts` 匯出**合併函式，只由 `index.ts` 匯出：`import-assembly-merge.ts` 用到 `import-assembly.ts` 的 `defaultAttachMessage`，反向匯出會形成循環匯入。
2. **合併後的訊息依各段的真實開始時間串接**（沒有時間的依合併紀錄順序排在後面），不一定是「目標在前」：把較早的對話拖到較晚的章節「⊕ 合併進 §N」時，若照目標在前串接，時間會倒退（伺服器會夾住）。`m${k}_` 的 k 仍依 `absorbedKeys` 的順序。
3. **使用者的 edits 不會被合併改寫**：工單寫「併入 `edits.messages[targetKey]`」，這裡是在 `applySessionMerges` 回傳的合併後 edits 裡做；狀態裡的 edits 一直是原始段落的語彙，寫入時經 `mergedOrigin` 轉回。這是拆回能無損的原因。
4. 掛到章節「排序移至該章節之後」實作為**章節正後方**（多篇保持彼此順序）。
5. 角色篩選與 `matchSession` 搜尋在合併後的段落上做（搜尋看合併後段落的標題與第一則提問）。
6. 分類區與章節目標也能「按下」套用到已勾選的段落，作為不拖曳的路徑（工單沒寫，協調者要求每個拖曳動作都有替代方式）。
7. 緊湊列的角色膠囊用短名稱（「§2」「↳ 支線」），避免在 372px 欄寬被截斷；無障礙名稱仍是完整的「§2 主線章節，…的角色」。
8. 工單 §4.3（合併回 main、重啟 :8120）依協調者指示未做；沒有 commit。

## 3. 無法無損還原的情況

- 合併後移動過順序，拆回時被併入的段落接在目標之後，不回到原本的位置。
- 合併後的段落在「主幹＋支線樹」裡改的**結論卡**存在目標 key 下；拆回後仍屬於目標段落，被併入段落的結論卡回到它合併前的內容。
- 合併後才設定的角色存在目標 key 下；被併入段落拆回後恢復合併前的角色。
- 目標段落如果本來就有字面上叫 `m1_…` 的訊息 id，會與改名後的 id 撞名（實際匯出不會出現這種 id）。
