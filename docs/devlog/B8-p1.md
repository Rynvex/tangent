## 1. 建議匣（共用機制）

- **資料**：`tangent_suggestion`（006，欄位同工作單，另加 `CHECK ((status = 'open') = (decided_at IS NULL))`）。
  partial unique index `(root_line_id, feature, kind, target_key) WHERE status = 'open'` 保證「同一對象同時最多一筆 open」（插入用 `ON CONFLICT … DO NOTHING`）；
  dismiss 的冷卻看 `(root, feature, kind, target_key)` 最新一筆 `dismissed` 的 `decided_at`。
- **不是一個功能**：功能在 `register` 裡用 `addSuggestionKind(kind, {permanentDismiss, accept})` 宣告自己會提的建議。只要有一個 kind 被註冊，
  `buildRegistry` 就掛上建議匣本身的掛勾（名稱 `suggestions`）。模式：任何一個會提建議的功能在這個 scope 是開的 → `modes["suggestions"] = on`。
  所以 `requireFeature(modes, FeatureSuggestions)`、`/capabilities`、路由（`FeatureConfigured("suggestions")` = 有註冊 kind）都照一般功能的規則走，核心沒有判斷式。
- **提出**：功能在 `AfterCommit` 呼叫 `e.proposeSuggestion(ctx, scope, {lineID, kind, targetKey, payload})`：自己的交易（鎖主線 → 查冷卻 → 插入），回傳要發的事件。
  失敗只記 log（建議不值得讓剛完成的寫入失敗）。被擋下（已有 open、冷卻中、永久拒絕、樹已封存）時什麼都不發。
- **接受**：`AcceptSuggestion(ctx, scope, id, body, opts...)` → 檢查建議匣與該功能都開、建議 open → 交給 kind 的 `accept(ctx, e, scope, s, body, mark, opts)`。
  `mark` 是一個 `InTx`，把建議標成 accepted；功能要把它放進「動作」的交易裡（例如階段 B 的 promote：`PromoteBranch(..., mark)`），
  或沒有動作時用 `e.acceptOnly`（`store.DecideSuggestion` 在同一交易跑功能的掛勾）。已經不是 open → `suggestion_not_open`，整筆回滾。
- **拒絕**：`DismissSuggestion`。`permanentDismiss` 的 kind 被拒絕後永遠不再提，其他的冷卻 `Limits.Suggestions.DismissCooldown`（預設 7 天）。
- **過期**（工作單二選一 → **兩個都做**）：
  1. 交易內：建議匣的 `OnBranchClosed` 掛勾在 merge / discard / promote / 順口問答完的同一交易裡，把關於這條支線（merge / discard 時含它底下的線；promote 時只有它自己，
     子支線被提升到主線還能用）的 open 建議改成 `expired`，commit 後發 `suggestion.changed`。
  2. 維護迴圈：`Maintain` 的工作 `suggestions.expire`（`TaskExpireSuggestions`）把「支線已結束但建議還 open」的清掉（政策把建議匣對某租戶關掉期間結束的支線，交易內的掛勾不會跑）。
  - 刪除整棵樹、順口問被清除：列跟著 `ON DELETE CASCADE` 消失（不是 `expired`）。
- **鎖順序**：提出、接受、拒絕都是 主線 → 建議列；在別的寫入裡接受（`MarkSuggestionAccepted`）是在那個寫入自己的鎖之後才碰建議列。沒有反方向的路徑。
- **事件** `suggestion.changed{rootLineId, suggestion}`，之後一個主線的 `line.updated`（open 數變了）。
- **`LineView`** 加 `openSuggestions`、`openSeeds`（只在主線；支線為 0）。hydrate 多一個查詢 `CountOpenInbox`（只對頁面裡的主線）。
- **測試用的功能 `SuggestionProbe()`**（`feature_probe.go`，名稱 `suggestion_probe`）：回覆裡有 `[probe:suggest]` 就對這條線提一筆 `probe`、
  `[probe:suggest-permanent]` 提 `probe_permanent`（拒絕是永久的）；接受只是接受，回 `{"accepted": true}`。fake runner 會回聲使用者訊息，所以送出含指令的訊息就會產生建議。
  不在 `catalog`（`/capabilities` 不列它，只讓 `suggestions` 變成開）、不在 `AllFeatures()`；參考伺服器可以用 `TANGENT_FEATURES=…,suggestion_probe` 開（smoke 與 e2e 用）。

## 2. `leaf` 收尾

- **資料**：`tangent_leaf`（006）。`line_id` 的外鍵指 `tangent_line`（不是 `tangent_branch`：階段 B 的 detach 會刪 branch 記錄，收尾要不要留給 B 決定）。
  `source_job_id` 非空 = AI 寫的、使用者還沒改過；`Leaf.aiDrafted` 由它推出（工作單「created_by 或欄位，選一種」→ 用 `source_job_id`）。`created_by` 是寫入目前內容的人（AI 寫的為空）。
- **`Leaf(mode, opts...)`**（有 AI，四種模式；`JobModel` 決定起草用的模型）：
  - `OnBranchClosed`：merge → 由卡片產生 `conclusion`（`domain.LeafFromCard`：line = 結論，截到 200 字；body = 問題 + 證據的註記與待辦，每項一行 `- `），`confirmed`，覆寫原有的收尾；
    discard 帶了 `leaf` → 寫入（`kind` 沒給就是 `dead_end`，其他四種也接受），`confirmed`。不合法 → `invalid_leaf`，整個 discard 回滾。
  - `AfterCommit`（suggest / auto）：discard 沒帶 `leaf` → 排 `leaf_draft`；promote → 替 `previous_main_line` 支線排 `leaf_draft`。job 經 `dispatchOrphanJobs` 交給 `SetJobDispatcher` 設定的派發器。
    **答完自動結束的順口問不排**（不是使用者丟掉的，成本不值得）；沒有任何對話訊息的支線也不排。
  - `JobHandler(leaf_draft)`（逾時 3 分鐘）：解析 `[LEAF-DRAFT]{kind, line, body?}`（只准這三個欄位，同卡片草稿的嚴格解碼）→ 鎖支線線 → 鎖 job → job done →
    沒有收尾或現有的是 AI 寫的 → 寫入（manual / suggest：`draft`；auto：`confirmed` 且 `aiDrafted`）；使用者寫的（含 merge 的卡片收尾）→ 不寫。跑失敗 / 不能用 → job `failed`，什麼都不寫。
- **Engine API**：`GetLeaf`（沒有 → `nil`）、`PutLeaf`（`confirmed`，清掉 `source_job_id`）、`DeleteLeaf`（沒有 → `leaf_not_found`）、`StartLeafDraft`（任何模式都可以；同支線 pending 的草稿被取代）、
  `DiscardBranchWith(ctx, scope, lineID, DiscardInput{Leaf}, opts...)`（`DiscardBranch` 不變，等於空的 `DiscardInput`）。主線 → `branch_not_found`；封存中 → `archived`。
- `BranchView.leaf: {kind, line, status} | null`（三個 view 查詢 `LEFT JOIN tangent_leaf`）。merge / discard 之後 Engine 重新讀一次支線（`reloadBranch`），回應與 `branch.changed` 才看得到同一交易寫的收尾。
- **事件** `leaf.changed{lineId, rootLineId, leaf | null}`（刪除時 `leaf: null`）。merge / discard 的順序：`branch.changed` → `line.updated` → `leaf.changed`。
- **不進 prompt**：沒有 `ContextProvider`；`[LEAF-DRAFT]` 加進 `domain` 的協定標記（從所有引用資料裡清掉，串流也會濾掉以它開頭的行）。

## 3. `parking` 停車場

- **資料**：`tangent_seed`（006，同工作單）。`expanded_line_id`、`note_id` 有外鍵（`ON DELETE SET NULL`）；`anchor_message_id` 沒有（訊息會搬、順口問會清除）。
- **`Parking()`**（開 / 關）。Engine API：`ListSeeds`（預設 open）、`CreateSeed`、`ExpandSeed`、`NoteSeed`、`DropSeed`。
- **建立**：`text` 壓成一行、1–500 字（`Limits.Parking.TextMaxRunes`）；每棵樹 open 最多 100（`Limits.Parking.MaxOpenPerTree`，`seed_limit`，extra `limit`）；封存中 → `archived`。
  `anchorMessageId` 給了就必須是這棵樹裡 `done` 的 user / assistant 聊天訊息（`anchor_not_found`）；**沒給 → 存「那條線當下最新的一則聊天訊息」**（線上沒有訊息 → NULL）。
- **展開**：`PlanSeedExpansion` 決定掛在哪裡 → 鎖外建背景包（同 `CreateBranch`）→ 一個交易：鎖 主線 → 父線 → 種子，套用建支線的所有檢查，建支線（`origin = seed`）、種子變 `expanded`。
  - anchor 被 move / promote 搬到別的線 → 跟著訊息，掛在它現在所在的線。
  - anchor 不見了（順口問被清除）或本來就沒有 → 掛在**主線最新的一則聊天訊息**；主線也沒有 → `anchor_not_found`。
  - anchor 所在的線已經結束 → 建支線的規則照常拒絕（`parent_closed` 之類）。任何拒絕種子都維持 open。
  - 目的預設是種子文字截到 200 字（`…`）；`kind` 預設 `investigate`（`aside` 需要 `aside` 功能）；provider / model 繼承父線。
- **記進紀要**：需要 `notes`（關閉 → `feature_disabled`，種子不變）。section 預設 `to_confirm`；文字截到紀要上限 400 字（種子上限是 500）；anchor 還在樹裡就當作紀要的來源訊息
  （所以有 `sourceLabel`）。同一交易：鎖主線 → 種子 → 寫紀要（revision +1）→ 種子 `noted` + `note_id`。
- **丟掉**：`dropped`。三種結束都是終態（`seed_not_open`）。
- **事件** `seeds.changed{rootLineId}`，之後主線的 `line.updated`（open 數）；展開另有 `line.created`、父線 `line.updated`、`branch.changed{created}`；記進紀要另有 `notes.changed`。
- 不呼叫 AI、不進 prompt。`domain.BranchOriginSeed`；`store.CreateBranch` 不接受別人傳 `origin = seed`（只有 `ExpandSeed` 用）。

## 4. 紀要 `sourceLabel`（核心）

- `tangent_note.source_label TEXT NOT NULL DEFAULT ''`；`Note.sourceLabel`（`omitempty`：舊資料與沒有來源的紀要不出現）。
- 寫入時在 store 的同一交易裡算（`domain.NoteSourceLabels.Render`），規則照前端 `note-source.ts`：來源線是主線且不是卡片 → 有來源訊息且它是主線上的聊天訊息時 `主線 #n`
  （n = 主線上 seq ≤ 它的 user / assistant 聊天訊息數，同 `chatNumbers`），否則 `主線`；卡片 → `結論卡・{標題}`；支線 → `{類型}・{標題}`。標題是目的，`previous_main_line` 用「原本的主線」。
- 語言：預設繁中（同產品介面）；`tangent.WithNoteSourceLabels(domain.EnglishNoteSourceLabels())` 或自訂模板（`{n}`、`{kind}`、`{title}`）。
- merge 的紀要、`ApplyNoteChanges`、取代、種子記進紀要都會帶。來源支線被刪除後照樣讀得到（測試直接刪支線線）。

## 擴充點的改動（核心，沒有功能判斷）

1. **交易內的掛勾可以排「commit 之後才發」的事件**：`txOutbox`（每次重試的交易開始時清空），`commit()` 在 AfterCommit 之前先發它。建議過期、收尾寫入都用它。
2. `txHooks` / `turnTxHooks` 改收 `txCall{modes, scope, kind, request, out}`；`txEvent` 加 `request`（核心呼叫的輸入，例如 `DiscardInput`）與 `out`；
   `commitEvent` 加 `promoted`、`request`、`out`。所有寫入（建立 / 搬移 / 展開 / merge / discard / promote / CompleteTurn）都照這個走。
3. `catalog` 加 `leaf`（有 mode，擁有輸入 `discard.leaf`）、`parking`、`suggestions`。`AllFeatures()` **沒變**（仍是第一批）。
4. `reloadBranch`：merge 與 discard 在 commit 後重讀支線（+1 查詢）。

## 其他修正

- `scripts/smoke.sh`：檢查 `branch.changed` 的 change 時用 `grep '^data: ' … | grep -q`，在 `set -o pipefail` 下 `grep -q` 提早結束會讓前一個 grep 收到 SIGPIPE、整條管線失敗；
  事件記錄變長之後約三成機率出現「no branch.changed renamed event」。改成單一 `grep -q` 讀檔。

- 參考伺服器：`TANGENT_FEATURES` 認得 `leaf[:mode]`、`parking`、`suggestion_probe`；預設加上 `leaf:suggest,parking`（不含 probe）。

## 與工作單 / 契約的差異

1. 種子上限與冷卻是 `domain.Limits` 的欄位（`Parking.MaxOpenPerTree`、`Suggestions.DismissCooldown`，另有 `Parking.TextMaxRunes`、`Leaf.LineMaxRunes` / `BodyMaxRunes`、`Suggestions.PayloadMaxBytes` 4 KiB），
   用既有的 `WithLimits` 設定，沒有另開 Engine 選項。
2. 過期兩種都做（交易內 + 維護迴圈），刪除的線則是列被串聯刪掉。
3. `/capabilities` 把建議匣列成一項 `{name: "suggestions", enabled}`（沒有 mode），不是加新欄位。
4. 測試用的建議來源做成**匯出的** `SuggestionProbe()`（httpapi 測試、smoke、e2e 都要用，封閉集合的 `Feature` 只能在 root 套件實作）。
5. `GET /leaf` 沒有收尾時回 200 `{leaf: null}`（不是 404）；`DELETE /leaf` 有做（204）。
6. 收尾的「AI 產生」用 `source_job_id`（`aiDrafted`），不是 `created_by`。
7. discard 的 `leaf.kind` 可以是五種之一，預設 `dead_end`。
8. 答完自動結束的順口問不排 `leaf_draft`。
9. `BranchView.leaf`、`LineView.openSuggestions` / `openSeeds` 在功能關閉時照樣帶出已存的資料（store 不知道功能；同 `summary` 關閉時 `LineView.summary` 照樣有）；`GET /suggestions` 只列開著的功能提的建議，所以政策把某個功能關掉時兩邊的數字可能不同。
10. 種子沒給 anchor 時存「建立當下那條線最新的一則聊天訊息」（工作單：分岔點 = 建立種子當下那條線的最後一則）；anchor 消失時退到主線最新的一則。
11. 種子記進紀要時文字截到紀要上限（400 字）。
12. `GET /seeds`、`GET /suggestions` 預設只列 open，`?status=` 可以給逗號分隔的狀態或 `all`。
13. `sourceLabel` 預設繁中，`WithNoteSourceLabels` 可換。

## 5. `spinoff`

- **資料**（`007_p1_spinoff`）：`tangent_line.origin_capsule JSONB`、`tangent_note.copied_from_note_id`、`tangent_link`（同工作單；兩端線 `ON DELETE CASCADE`，訊息 id 沒有外鍵）。
- **`Spinoff()`**（開 / 關）。`Engine.Spinoff(ctx, scope, lineID, SpinoffInput{Mode, AtMessageID, Title, CopyNotes}, opts...)`、`Engine.ListLinks`。
- **detach**（`store.Detach`）：鎖 主線 → 父線 → 支線 → 子樹（id 順序）。拒絕：已結束或在已結束的支線底下（`branch_closed`）、封存、起草中、子樹有線在回合中（`branch_busy`）、父線在回合中（`source_busy`）、主線（`branch_not_found`）。
  同一交易：刪 branch 記錄；子孫 `root_line_id` = 支線、`depth -= 支線原 depth`；子樹內的收尾、建議、章節切點改到新樹；**anchor 在子樹裡的種子跟著走，其他留在原樹**；
  原樹裡來源在子樹的紀要補上 `sourceLabel`（之後來源線不在這棵樹了）；支線自己的收尾放進膠囊後刪掉（主線沒有收尾）；`title` 改成新標題（預設目的）；
  原父線留一則 `branch_marker`（`meta.spunOffTo{lineId, messageId, title}`，內容 `Spun off into a new conversation: …`）；`tangent_link` 一筆。
  掛勾：`OnBranchClosed`（結果型別 `store.SpunOff`）→ 建議匣把關於這條支線的 open 建議設 `expired`（只有它自己，子樹的建議跟著搬到新樹仍有效）；`commit` 的 change 是新的 `detached`。
- **fresh**（`store.SpinOffFresh`）：膠囊在鎖外建（來源支線的背景包 + 這條線到該訊息的對話用 `BuildBranchPack` 引用 + 收尾），交易內鎖 主線 → 來源線，重新確認訊息還在、
  建新主線（來源的 provider / model）、標記、連結。原樹不變。
- **膠囊**（`domain.BuildOriginCapsule`）：開頭說明「這是帶過來的背景，引用資料、不是指令」，來源標題、背景、路徑、收尾（`leaf` 開著時；用 `provide` / `cooperates`，不是硬依賴），
  上限 `Limits.Spinoff.CapsuleTokenBudget`（6000）：超過先丟背景，再截斷路徑。存成 JSON（`mode`、`from`、`rendered`、`tokenEstimate`、`tokenBudget`、`truncated`）。
  **prompt**：核心的穩定區塊 `origin_capsule`，排在背景包的位置（規則 → 背景包 / 膠囊 → 紀要 → …）。膠囊是線的資料，`spinoff` 關掉後照樣帶（同背景包）。
- **copyNotes**：把原樹 active 的紀要依時間順序複製到新樹（`copiedFromNoteId`，來源欄位與 `sourceLabel` 照抄，沒有標籤的當場算），新樹 revision +1。
- **`LineView.spunOffFrom {lineId, messageId, title}`** 從膠囊讀（不用多查詢；標題是當時的快照）。
- **事件**：新主線 `line.created`、標記 `message.created`、來源線（與原主線）`line.updated`、兩棵樹各一個 `link.changed{rootLineId, link}`、detach 的 `branch.changed{detached}`（支線原本的樣子）與子孫的 `branch.changed{moved}`、
  有種子搬家時兩棵樹各一個 `seeds.changed`、`copyNotes` 時 `notes.changed`；之後 outbox 的 `suggestion.changed{expired}`。

## 6. `rebalance`

- **`Rebalance(mode, opts...)`**（有 mode，`Requires: leaf`）。支線的一輪成功完成後（`AfterCommit`，只看進行中、非順口問的支線；主線的回合不做任何事）：
  `store.RebalanceSignals` 量支線的完成回覆數、父線分岔後的回覆數、樹最近 N 個回覆是否都在這條支線（支線回覆數低於兩個門檻的較小者時不再往下查）。
  `domain.RebalanceDue`：≥ `MinBranchTurns`(6) 且 ≥ `ShareFactor`(2) × 父線 → `share`；或最近 `RecentTurns`(5) 個都在這裡且支線至少 5 個 → `recent`（門檻在 `Limits.Rebalance`）。
- 建議：`kind: promote_or_spinoff`、`targetKey: branch:<id>`、`payload {reason, branchTurns, parentTurns, recentInBranch, actions}`；`actions` 是現在能做的
  （`promote`：直接掛在主線下；`spinoff`：`spinoff` 開著）。兩個都不行（深層支線而 spinoff 關閉）就不提。拒絕 = 永久。manual 不提；auto = suggest。
- **接受** `{action: promote}` → `PromoteBranch`（`leaf` 在 suggest / auto 時照舊替前主線排 `leaf_draft`）；`{action: spinoff, title?, copyNotes?}` → detach（`spinoff` 關閉 → `feature_disabled`）；其他 → `invalid_input`。
  結果 `RebalanceResult{action, line, branch?, previousMainLine?, link?}`。
- **接受標記先跑**：新的內部 `inTxFirst`：建議匣的 `mark` 在功能的交易內掛勾**之前**執行，否則 promote / detach 關掉支線時建議匣會先把這筆建議設成 `expired`，`mark` 就失敗。
