## 1. `open_loops`（`OpenLoops()`，開 / 關，只讀）

- `Engine.OpenLoops(ctx, scope, OpenLoopsInput{LineID, StaleDays})` → `OpenLoopsList{rootLineId, staleDays, staleBranches, toConfirm?, seeds?, suggestions?}`；`GET /open-loops?root=&staleDays=`。
- 開太久 = `status = open` 且支線線的 `last_activity_at` 早於 `now − staleDays`（預設 `Limits.OpenLoops.StaleAfter` = 3 天；`staleDays` 1–365）。最久沒動的在前。
- 只列開著的功能：`toConfirm` 要 `notes`、`seeds` 要 `parking`、`suggestions` 要建議匣（只算開著的功能提的，同 `GET /suggestions`）；關著的類欄位不存在。`staleBranches` 一定有（核心資料）。
- 每類 `items` ≤ `MaxPerKind`（50），`total` 是 `count(*) OVER ()`（同一個查詢）。封存的樹不列；`root` 是任何一條線（解析到主線），別的租戶 → `line_not_found`。
- **`LineView.staleBranches`（提案，已實作）**：主線上的「開太久的支線」數，併進 hydrate 既有的 `CountOpenInbox`（多一個子查詢，不多一次往返），門檻用 `Limits.OpenLoops.StaleAfter`。
  「待處理」= `staleBranches + openSeeds + openSuggestions`。時間經過本身不會發事件（下一次讀到時才變）。不看功能開關（同 `openSeeds`）。

## 2. `goal`（`Goal(mode, opts...)`，有 AI）

- **Engine API**：`GetGoal`（沒有 → `nil`）、`PutGoal`（`source: manual`）、`DeleteGoal`（沒有 → `goal_not_found`）、`ProposeGoal`（→ `goal_propose` job）。`{lineId}` 可以是樹上任何一條線，一律解析到主線；
  寫入鎖主線（`lockSeedRoot`：主線 → 封存檢查），所以「接受提案」（主線 → 建議列）照建議匣的鎖順序。事件 `goal.changed{rootLineId, goal | null}`。
- **prompt**：`ContextProvider` 讀 `GoalOfRoot`（一個 PK 查詢；BeginTurn 時根已在鎖內決定）→ `PromptInput.Goal` → 內建區塊 `goal`（保留鍵），`BuildGoalBlock` 用一行引用（去標記、壓成一行），
  `stableSectionOrder` 改成 規則 → **目標** → 背景包 / 起始膠囊 → 紀要 → 宿主區塊 → …。整棵樹（含支線、岔題）都帶。目標在 `ChatBlocks` 的穩定段（Anthropic 快取斷點之前）；改目標會讓快取失效一次。
  功能關閉（設定沒開或政策關掉）時不帶，已存的目標保留。
- **提案**（`goal_propose` job，逾時 3 分鐘）：讀主線最前面 12 則中完成的對話（`BuildGoalProposePrompt`，回 `[GOAL-PROPOSE]{"goal": …}`，嚴格解碼）。
  - 何時：按鈕（任何模式）；suggest / auto 在**主線第 2 個回覆**完成後、還沒有目標時自動提一次（`AfterCommit`）。主線沒有完成的對話 → `no_messages`。同一條主線進行中的提案被取代（`Supersede`）。
  - 結果：suggest / manual → 建議匣 `goal_propose`（`targetKey goal:<主線>`，`payload {text}`）；**按鈕提出的不受之前拒絕的冷卻限制**（store 的 `ProposeInput.Asked`）。
    auto → 直接寫成目標（`source: ai`）：自動提的不覆蓋已有目標（`PutGoalInput.KeepExisting`），按鈕提的覆蓋。執行失敗 / 輸出不能用 → job `failed`（固定文字），什麼都不寫。
  - 接受：本文 `{text?}`；沒給或相同 → 提案文字（`ai`），改了 → 使用者的文字（`manual`）。目標寫入與建議標成 accepted 在同一交易（`inTxFirst` 的 mark），`result = {goal}`。
- **偏題偵測**（`drift_check` job，逾時 3 分鐘）：suggest / auto、**主線**的一輪成功完成後，主線完成的回覆數是 `Limits.Goal.DriftEvery`（4）的倍數且有目標時排一個 job；
  讀最近 `2 × DriftEvery` 則完成的對話與目標（`BuildDriftCheckPrompt`，回 `[DRIFT-CHECK]{"drift": false}` 或 `{"drift": true, kind, purpose, reason}`）。
  偏題 → 建議匣 `drift`（`targetKey drift:<這次的回覆 id>`，`payload {anchorMessageId, kind, purpose, reason, goal}`；`kind` 只在 `aside` 開著時可能是 `aside`）。
  接受：本文 `{kind?, purpose?}` 覆寫 → `CreateBranch(anchorMessageId, …, mark)`（建支線的所有檢查都照常；被拒絕時建議維持 open），`result = {line, branch}`。
  先查回覆數（一個 count 查詢），不是 2 或倍數就不讀目標，主線回合平常只多一個查詢。
- manual：只有目標與按鈕，不自動提案、不偵測偏題。

## 3. `relations`（`Relations(mode, opts...)`，有 AI）

- **Engine API**：`CreateRelation(ctx, scope, lineID, RelationInput{From, To RelationEnd; Label}, opts...)`、`DeleteRelation(ctx, scope, lineID, relationID, opts...)`、`ListRelations`。
  `GET/POST /lines/{id}/relations`、`DELETE /lines/{id}/relations/{rid}`。存成 `tangent_link`（kind `relation`）。
- **端點**：線，或那條線上的一則訊息（完成的 user / assistant 聊天訊息或結論卡，同釘選的規則）。`From.LineID` 預設路徑的線，且必須在路徑那棵樹（`invalid_input`）；`To` 可以是同租戶的任何對話（跨樹）。
  別的租戶的線 → `line_not_found`；訊息不在那條線上 → `message_not_found`；兩端相同 → `invalid_input`；同兩個地方已有關聯（不分方向）→ `relation_exists`。
- **上限**：碰到的每棵樹（起點與終點的樹）的關聯數都要 < `Limits.Relations.MaxPerTree`（200）→ `relation_limit{limit}`。
- **鎖**：兩端的主線依 id 排序後加鎖（`lockRoots`，同一棵樹只鎖一次；封存 → `archived`），鎖內重新確認兩條線還在原本的樹（detach 同時發生 → 可重試的錯誤，整筆重跑）與訊息。
  其他寫入都是「一個主線 → 它的子孫」，沒有人先鎖子孫再鎖主線，所以兩個主線依 id 的順序不會形成環（`TestP2Concurrency_RelationsRacingADeletedTreeNeverDeadlock`）。
- **訊息端點會跟著訊息走**：列出時 `LEFT JOIN tangent_message` 取訊息**現在**所在的線（move / promote 之後）；過濾仍用存的線 id（有索引）。move / promote 都在同一棵樹裡，存的線 id 仍在這棵樹；
  唯一會換樹的是 detach，所以 `store.Detach` 多一個 `RehomeLinkEnds`：訊息在被獨立的子樹裡的連結端點改成那則訊息現在的線（所有種類）。
- **事件**：`link.changed{rootLineId, link, deleted?}`，碰到的每棵樹各一次（`LinkChange` 加 `deleted`）。
- **建議**（suggest；auto 等同 suggest，關聯只在使用者接受時畫）：非岔題的支線 merge / discard 後（`AfterCommit`），若同一棵樹有別的支線，排 `relation_suggest` job（逾時 3 分鐘）：
  候選是其他支線（新的在前，最多 30 條），用短鍵 `B1…` 呈現目的與收尾（或卡片結論），回 `[RELATION-SUGGEST]{"relations": [{to, label}]}`（最多 3 筆、只收認得的鍵）。
  每筆提成 `relation` 建議：**`lineId` 是主線**（結束的支線上的建議會立刻 expired，也不能再提）、`targetKey relation:<id>:<id>`（兩條線依 id 排序，不分方向）、`payload {fromLineId, toLineId, fromTitle, toTitle, label}`。
  接受：本文 `{label?}` → `CreateRelation(..., mark)`，`result = {link}`。manual 不提。
- **`/links`**：`spinoff` **或** `relations` 設定了就掛（route 加 `orFeature`）；`Engine.ListLinks` 只列開著的功能的種類，兩個都關 → `feature_disabled`（名稱是 `spinoff`，只設定了 `relations` 時是 `relations`）。

## 4. 訊息釘選（核心）

- `domain.Message.Pinned`（`json:"pinned"`）；`Engine.PinMessage(ctx, scope, messageID, pinned, opts...)`；`POST/DELETE /messages/{mid}/pin` → `{message}`。不需要任何功能。
- 只有完成的 user / assistant 聊天訊息與結論卡可以釘（其他 → `invalid_input`）；封存 → `archived`；沒有 / 別的租戶 → `message_not_found`。
- 鎖訊息現在所在的線；鎖住後訊息已被搬走 → 可重試的錯誤整筆重跑（`TestP2Concurrency_APinFollowsAMessageMovedMeanwhile`：與 move 同時跑 5 次，釘選都留在搬過去的訊息上）。
- 狀態有變才發 `message.updated`（帶主線 id）；沒變就不發。釘選欄位跟著訊息走（move / promote 不改它）。`fisheye`（階段 B）用它當先天重要性。

## 與工作單 / 契約的差異

1. 刪除關聯是 `DELETE /lines/{id}/relations/{rid}`（工作單寫 `DELETE /lines/{id}/relations`，但刪除需要關聯 id；放在路徑同 `/notes/{nid}`、`/milestones/{mid}`）。
2. 偏題偵測只看**主線**（支線本來就是岔出去的話題，用支線目的約束），以主線完成的回覆數是 `DriftEvery` 的倍數為準。
3. 目標的自動提案：suggest / auto 在主線第 2 個回覆後、沒有目標時提**一次**（之後只有按鈕）。auto 直接寫入（不覆蓋已有的；按鈕提的覆蓋）。
4. 關聯的 auto 等同 suggest（同樹平衡）；建議在支線 merge / discard 時觸發，`lineId` 是主線（不然會跟著結束的支線 expired）。
5. 關聯的起點必須在路徑那棵樹；同兩個地方不分方向只能一條（`relation_exists`）；上限兩端的樹都算。
6. 訊息端點的 `fromLineId` / `toLineId` 回報訊息**現在**所在的線（所有種類的連結都是，spinoff 也是；樣本沒有變，因為流程裡沒有搬過分岔訊息）。

## 2. `fisheye`（`Fisheye()`，開 / 關，需要 `leaf`）

# B9.1（2026-10-17）：合併時改掛進行中的子支線

> 協調者回覆階段 C 的第 3 題。沒有 commit；沒有動 `web/`、`docs/DESIGN.md`。

## 做了什麼

- `store.CombineBranches` 在同一交易裡，關閉舊支線、建新支線、設 `merged_into_line_id` 之後，把舊支線**直接**底下 `status = open` 的子支線改掛到新支線（`ListOpenChildBranches` → `ReparentBranches`），再重讀新支線的 `LineView`（`branchCounts` 算進它們）。
  結果多 `Reparented []string`（id 順序）；Engine 的 `CombinedBranches.Reparented`、HTTP 回應的 `reparented`。
- **鎖順序**：主線 → 父線 → 被合併的支線（id 順序）→ 它們進行中的子支線（id 順序）。子支線的子孫不用鎖（它們的 branch 記錄不變）。
- **上限**：改掛的數量超過 `Limits.Branch.MaxOpenPerParent` → `branch_limit`，整筆合併回滾（新支線在建立時沒有子支線，所以就是「改掛數 > 8」）。
- **深度**：新支線是舊支線的兄弟（同一個父線、同一層），所以子支線與它們底下的 depth 都不變；不需要像 move 那樣位移，也不會碰到硬深度。
- **事件**（commit 之後）：每條改掛的子支線 `branch.changed{moved}`，失去子支線的舊支線各一個 `line.updated`，排在舊支線的 `branch.changed{discarded}` 之後。

## anchor 的選擇（記錄）

合併不複製訊息：新支線的背景包只**引用**每條舊支線最近的 8 則對話。所以子支線分岔的那則訊息沒有一份在新支線上。考慮過的選項：

1. **維持原本的 anchor（採用）**：`anchor_message_id` 不變，仍指向它真正分岔的那則訊息（留在已放棄的舊支線上，照樣讀得到；在最近 8 則裡時新支線的背景包也引用了它）。
2. 改成新支線自己的 anchor（新支線在祖父線上的分岔訊息）：那則訊息不在新父線上，而且會讓子支線看起來是從別處分岔的，不採用。
3. 等新支線有第一則訊息再改掛到那裡：合併當下沒有訊息，而且子支線不是從那則訊息分岔的，不採用。

讀 anchor 的程式都檢查過：建支線 / 背景包只在建立時讀；`move` 與 `promote` 只看「掛在自己線上的訊息」的分岔（`ListBranchesAnchoredIn`、`ListBranchAnchorsInLine`），所以不會誤動這些子支線；
樹平衡的「父線分岔後的回覆數」找不到 anchor 在父線上時從頭算，對改掛的子支線正好是「新支線的所有回覆」（它在合併前就分岔了）；種子展開沿分岔點往上走時，會走到舊支線（已結束）再往上，行為合理。
**DESIGN §5 的「anchor 必須是父線上 done 的訊息」從此只在建立時成立**；改掛後的子支線是例外（建議寫進 §12）。
